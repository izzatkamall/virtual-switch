Threads

My switch runs as one process. When a host connects it gets a port, and every port has two threads, one for reading (rx) and one for sending (tx). On top of that there are some threads that only run once.

host A  <-->  [port 0: rx thread, tx thread]
host B  <-->  [port 1: rx thread, tx thread]      main thread (accepts new hosts)
host C  <-->  [port 2: rx thread, tx thread]      signal thread
                                                  admin thread  <-- swctl
              rx of one port puts frames          rate thread
              on the queue of another port        aging thread
                                                  logger thread --> switch.log

What each thread does:

  • main: blocks the signals, starts the other threads, then waits for a free port and accepts new hosts. If no port frees up in time it sends the host a "switch full" frame and closes it. At the end it does the shutdown.
  • rx (one per port): reads frames from its host, learns the source MAC, finds where the frame should go and puts it on that port's queue (or on every port in the VLAN for broadcast or unknown MACs).
  • tx (one per port): waits until its queue has something, picks the next frame by priority, waits for a token if the port is rate limited, and sends it to the host.
  • signal: waits with sigwait. SIGINT/SIGTERM shut the switch down, SIGHUP reloads the config, SIGUSR1 dumps the MAC table to a file.
  • admin: listens on the UNIX socket for swctl commands and replies.
  • rate: every 100ms adds tokens to each port's token bucket.
  • aging: every second removes MACs that haven't been seen for a while.
  • logger: takes messages off the log queue and writes them to switch.log, so no other thread has to wait for the file.

None of the threads busy wait. They sleep on a condition variable, a semaphore, sigwait or a blocking socket call. The rate and aging threads use pthread_cond_timedwait instead of sleep so that shutdown can wake them up straight away.

Locks

  • attach_lock: held while picking a port for a new host and during swctl shutdown/up. It keeps the free ports semaphore in sync with which ports are turned on.
  • port lock (one per port): protects everything about that port, like its socket, its state (free, up, closing, done), its three priority queues, its VLAN, the mirror setting and the token bucket.
  • MAC table bucket locks (16 of them): each one protects the list of MAC entries in its bucket. Because there are 16, two threads learning different MACs usually don't block each other.
  • count_lock: protects the total number of MACs, the limits, and how many MACs each port has (for port security).
  • stats mutex: protects the in/out/dropped/mirrored counters in shared memory. It is process shared so swctl can lock it too.
  • cfg_lock: protects the current config, since SIGHUP can change it while the switch is running.
  • log lock: protects the log message queue.
  • stop_lock: protects the "stopping" flag used during shutdown.

I also use a semaphore to count free ports, and each frame has an atomic reference count. A broadcast frame is only stored once, every queue it goes into adds one to the count, and the last one to finish with it frees it.

Lock order

I always take locks in this order and never hold two port locks at the same time:

  1. attach_lock
  2. one port lock
  3. MAC bucket locks, lowest number first if I need more than one
  4. count_lock
  5. stats mutex, cfg_lock, log lock, stop_lock. Nothing else gets locked while holding one of these.

Some examples of how I stuck to it. When a frame comes in, the rx thread locks its own port, reads the VLAN and mirror setting, and unlocks before it touches any other port. Then it locks each output port one at a time. Mirroring is the same, the copy is queued after the first port is unlocked. When the MAC table is full, the oldest entry is removed after the bucket lock is let go, not while holding it. "clear mac" locks all buckets from 0 to 15 and then count_lock. swctl shutdown takes attach_lock and then the port lock, and the rx thread never needs attach_lock to finish, so it can't get stuck waiting on it.

A bug I hit

For the priority queues each port has three queues (high, normal, low) and the tx thread sends 5 high, then 3 normal, then 1 low. To stop low priority from starving I added aging. My first version did aging per frame: if any frame had been waiting more than 200ms, send it next.

My priority test failed 3 out of 5 times. In that test host B stops reading, and host A sends 40 low, then 40 normal, then 40 high frames. The high frames should jump ahead, but they were coming out last, the same order they went in.

It took me a while to see why. Because B wasn't reading, the queues stayed full for a long time, so every frame ended up waiting more than 200ms. That means every frame counted as "old", and "always send the oldest frame" is just first in first out. The aging was taking over completely instead of only helping a queue that was being starved.

I fixed it by doing aging per queue instead of per frame. A queue only gets an extra turn if it has frames and hasn't been served at all for 200ms. After that turn its timer starts again and the normal 5:3:1 order carries on. I added a unit test for this case where all the frames are old, and it checks that 27 sends still come out as 15 high, 9 normal and 3 low. The priority test passes every time now.

Something related I found before that: the priorities did nothing at all at first. The kernel's send buffer for each socket was big enough to take every frame straight away in order, so my queues were always empty. I set SO_SNDBUF to 8KB on each host socket so the frames wait in my queues where the priorities can actually reorder them.

Testing

The tests are in the GitHub repo (they are not in the submission zip). "make check" runs all of them, 3 unit tests in C and 12 tests in Python that each start a fresh switch. They test forwarding, a host that never reads, broadcast storms with hosts joining and leaving, port security, the port limit, priorities, rate limiting, VLANs, the swctl commands, mirroring, shutting down with Ctrl+C in different situations, and a stress test that runs traffic and about 30,000 random swctl commands at the same time.

"make tsan" and "make valgrind" run the same tests with ThreadSanitizer and valgrind. TSan found one race. At shutdown, close_all_ports() was setting a port's state back to free without locking the port, while rx threads of other ports could still be reading it. I moved that write under the port lock and after that TSan was clean. Valgrind shows no errors, no leaks and no sockets left open.
